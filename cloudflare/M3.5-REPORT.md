## A. CPU Optimization

### A.1 Pipeline và nguồn CPU

| Bước | Trước M3.5 | Sau M3.5 |

| Zod validation | Worker | Worker |
| Markdown/HTML parse + sanitize | Worker → DO | **DO** |
| Plain-text/read time | Worker | **DO** |

**Nguyên nhân CPU cao trước đây:** Worker vừa parse content, vừa gọi DO sanitize, rồi làm plainText/FTS/revision/audit/serialize; nội dung 8–30 KB làm P50 8–10 ms. D1 latency không phải CPU, nhưng nhiều subrequest/parse/serialize cộng dồn.

### A.2 Phương án đã chọn: B — DO offloading theo client

- DO instance **`content:<api_client_id>`**, không dùng một DO toàn cục.
- Mỗi client có một instance; request cùng client tuần tự (an toàn idempotency/ghi), client khác chạy song song.
- Auth/rate vẫn DO riêng (`rate`), sanitize nằm trong content DO.
- Không chọn Async Publishing vì phải đổi contract `202 Accepted`, thêm job state/polling/queue và phức tạp vận hành; DO giải quyết CPU trước mắt.
- Không chọn chỉ tối ưu Worker (A) vì 8–30 KB vẫn vượt P50 7 ms.

## B. Media Storage Analysis ($0)

| Phương án | Free/điều kiện | Dynamic upload? | Rủi ro/chi phí | Kết luận |
|---|---|---|---|---|
| **R2 Free** | 10 GB, 1M Class A, 10M Class B, egress free; **cần R2 subscription/billing** | Có | Overage bị tính phí, không hard-stop; cần guard | Tốt về kỹ thuật nhưng **BLOCKED** cho đến khi được duyệt billing |
| **Workers Static Assets** | 20k file, 25 MiB/file; request miễn phí | Không; chỉ build-time | Upload động cần rebuild/deploy; 20k file cap | Dùng cho 61 ảnh legacy; **không phải giải pháp upload động** |
| **External free storage** (B2/Supabase/Cloudinary…) | Free tier thay đổi, cần account/ToS, có thể cần billing | Có | Phụ thuộc nhà cung cấp, giới hạn/hotlink/xóa file/khóa tài khoản; chưa được duyệt | **Không tích hợp** trong M3.5 |
| **External image URLs** | AI gửi URL nguồn khác | Không upload | Ảnh có thể chết/hotlink/copyright; không fetch server-side để tránh SSRF | Chấp nhận làm `cover_image` HTTPS; cần validate + fallback |

**Khuyến nghị $0 hiện tại:**
- Giữ ảnh legacy trong Static Assets.
- Media upload/API `POST /media` trả **501** trung thực; Admin media library chỉ hiển thị legacy + thông báo R2 chưa bật.
- Cho phép `cover_image`/`og_image` là HTTPS external URL (schema đã validate), **không fetch server-side**.
- Khi cần upload động: chỉ R2 sau khi có billing profile + guard (cap 8 MB/file, 1 ảnh/bài, soft cap 5 GB, audit, lifecycle, cảnh báo) hoặc nhà cung cấp ngoài được phê duyệt riêng.
- Media adapter `src/media.js` giữ nguyên để tích hợp sau.

**Trạng thái media:** **BLOCKED / NOT VERIFIED** — không có upload remote, không có media parity.

## C. API Contract & Security

### C.1 Kiểm thử

- M3 API: **28/28 PASS** sau khi offload.
- M2.5 API client lifecycle: **16/16 PASS**.
- M2 functional: **74/74**; security **17/17**.
- M1 public regression: **42/42**.

Đã kiểm tra:
- create/get/list/update, publish, schedule, unpublish, delete, slug lookup.
- idempotency replay/conflict, external_id replay.
- review mode demotion, auto mode, scope read-only.
- validation, content cap, XSS sanitize, media 501.
- API key rotation/revocation immediate denial.
- Audit entries.
- Public visibility/scheduled/cron/410.

### C.2 Concurrency / lost updates

- Create/update được serialize theo **từng API client** trong content DO; idempotency và external_id nằm trong cùng DO.
- Publish/unpublish/delete vẫn chạy ở Worker + D1; chưa có optimistic version/ETag. Hai request sửa đồng thời có thể last-write-wins. **PARTIAL** — phù hợp AI một writer/client; cần version check nếu nhiều writer.
- Không thay đổi API contract; nếu cần stale-write protection sẽ dùng `If-Unmodified-Since`/version ở milestone sau.

### C.3 Security

- Content sanitize trong DO; script/XSS bị loại.
- Request body cap 1 MB; content schema max 200k; rate limit client/IP.
- Không fetch external media URL server-side → không SSRF qua cover.
- API key hash-only; revoked key 401.
- DO per client tránh single global contention; vẫn cần theo dõi DO concurrency.
- WAF/Access/edge cache vẫn **NOT VERIFIED**.
